# Contributing to Storycreep

Thank you for helping. This page covers how the project is organised, the contributor licence agreement, and how to build and check your change.

## How the work is organised

- [`docs/PRD.md`](docs/PRD.md) is the contract. Every functional requirement has a stable ID (such as `FR-EDIT-02`) and acceptance criteria. If the code and the PRD disagree, the PRD wins until it is amended.
- [`docs/IMPLEMENTATION_PLAN.md`](docs/IMPLEMENTATION_PLAN.md) cuts the PRD into an ordered list of pull requests. Its standing checklist applies to every pull request.
- If a requirement turns out to be wrong or unbuildable, amend the PRD first, with a row in its document history, and then the plan. The plan's "Rules for every edit" say what each edit must keep true.

## Contributor License Agreement

Storycreep is licensed under AGPL-3.0-only, except the Godot addon in `godot/addons/storycreep/`, which is MIT so that games can include it freely. Before your first pull request can be merged, you sign the [Contributor License Agreement](CLA.md).

**Why.** The CLA lets the maintainer offer Storycreep under other terms later, such as a commercial licence alongside the AGPL, without having to find and ask every past contributor (PRD ADR-011). Without it, a licence change would need the consent of everyone who ever contributed.

**What it does not do.** You keep the copyright in your work. The CLA is a licence grant, not a transfer of ownership. Your contribution is still published under the project's licence.

**How to sign.** When you open your first pull request, the CLA bot comments on it with a link to the agreement. To sign, post this comment on the pull request:

> I have read the CLA Document and I hereby sign the CLA

The bot records your GitHub user name and user ID, the ID of your comment, the pull request number, and the date in the `cla-signatures` branch, where they are public. You sign once; later pull requests pass automatically. If the check does not update, comment `recheck`.

## Development setup

The required tools run natively on Windows ARM64, macOS, and Linux. No tool in the workflow may need x86 emulation or WSL (PRD §9.9), and CI checks this by running on `ubuntu-latest`, `windows-11-arm`, and `macos-latest`.

- **Go** 1.26 or newer.
- **Node.js** 24 (see `.nvmrc`).
- **pnpm** at the version pinned in `package.json`. With Node.js 24, `corepack enable pnpm` installs it.
- **Docker**, for the server's database tests, which run PostgreSQL in a container (PRD NFR-Q-01), and the tests of the S3 driver of the assets' storage, which run MinIO in one: Docker Desktop on Windows and macOS, Docker Engine on Linux.

Then install the JavaScript dependencies, and the browser that the web app's end-to-end tests run in:

```sh
pnpm install
pnpm --filter @storycreep/app exec playwright install chromium
```

Playwright has no build of Chromium for Windows on ARM64, whose x64 build would run emulated, so there the tests run in Windows's own Edge, which needs no install, and the second command can be skipped.

## The container image

`deploy/Dockerfile` builds the container image (PRD FR-ADMIN-01 AC4), and `deploy/docker-compose.yml` runs it with PostgreSQL (FR-ADMIN-07). [`deploy/README.md`](deploy/README.md) describes both, and how to run the development compose file. The tests in `server/internal/deploy` check them:

- `go test ./...` checks the compose files' contents, on every OS. The published compose file must pass every configuration key to the server, so a new key needs a line in its `environment`, in `deploy/.env.example`, and in `deploy/README.md`.
- The image's tests need Docker, and skip without an image to test. CI's image job runs them on a `linux/amd64` and a `linux/arm64` runner: it builds the image for both platforms into an OCI archive, whose platforms, user, and files `STORYCREEP_TEST_IMAGE_ARCHIVE` lets the tests check, and loads the runner's platform's image, which `STORYCREEP_TEST_IMAGE` names and the tests start `docker-compose.yml` with.

To run them locally, build both from the repository's root, with the archive outside the repository:

```sh
docker buildx build --platform linux/amd64,linux/arm64 -f deploy/Dockerfile --output type=oci,dest=/tmp/storycreep.tar .
docker build -f deploy/Dockerfile -t storycreep:test .
```

Docker Desktop builds both platforms as it is. Docker Engine may need a builder that can, which `docker buildx create --use --driver docker-container` creates. Then run, in `server/`:

```sh
STORYCREEP_TEST_IMAGE_ARCHIVE=/tmp/storycreep.tar STORYCREEP_TEST_IMAGE=storycreep:test go test ./internal/deploy
```

The compose test publishes the server on `127.0.0.1:7777`, the documented port, or on another port if something already listens there, and removes its containers and volumes when it is done. Every CI run on the main branch, after a push and weekly, publishes the image of its commit to `ghcr.io/cybercute-studio/storycreep`, once its checks pass, tagged `sha-<commit>`, and `main` unless `main` already has a newer commit, as when an older run is re-run. GitHub creates a new package as private, so after the first publish a maintainer makes the package public, once, in its settings on GitHub: until then, `docker-compose.yml` cannot pull the image without signing in.

## Tagging tests with requirements

Every test that proves an acceptance criterion names it, so that the traceability report can map the PRD to the tests. Write a line comment that starts with `Verifies:` directly above the test declaration, with no blank line between them. List acceptance criteria as `FR-…/ACn` and non-functional requirements as `NFR-…`, separated by commas. Spell every ID in full, so that searching for `FR-EDIT-02/AC3` finds every test of that criterion.

Go tests, benchmarks, and fuzz tests, and their subtests (`t.Run` or `b.Run` called on a `*testing.T` or `*testing.B` parameter), in `*_test.go` files. The report names a subtest as `go test` does, such as `TestMoveNode/keeps_connections` (each space character becomes `_`, and a name used again in the same test or subtest is numbered, as `keeps_connections#01`), with `*` for a name that is not a literal:

```go
// TestMoveNode checks that a moved node keeps its connections.
//
// Verifies: FR-EDIT-02/AC3, NFR-PERF-01
func TestMoveNode(t *testing.T) {
```

Vitest and Playwright `test` and `it` declarations with a literal title (a string with nothing added to it, and no `${…}`), in `*.test.ts` and `*.spec.ts` files, and Vitest `bench` declarations in `*.bench.ts` and `*.benchmark.ts` files (or `.tsx`, `.js`, and the other script extensions). A `bench` in a test file, or a `test` or `it` in a benchmark file, is not a test the report can name: Vitest's test run reads only test files, and `bench` runs only in its benchmark run:

```ts
// Verifies: FR-EDIT-02/AC3
test("a moved node keeps its connections", () => {
```

A declaration may carry the modifiers `only`, `skip`, `todo`, `fixme`, `fail`, `fails`, `concurrent`, `sequential`, `shuffle`, `serial`, and `parallel`, as in `test.describe.serial`, however Biome splits it across lines, and Vitest's `skipIf` and `runIf` with their condition, as in `test.runIf(isLinux)("…", …)`. A hook such as `test.beforeEach`, and a declaration with `each` or `for`, is not a test the report can name. A group (`describe`, `test.describe`, or Vitest's `suite`) runs nothing itself, so tag the tests in it; the report fails on a `Verifies:` comment above a group. The report names a test after the groups it is in, as Vitest does: `group > title`, with `*` for a group whose title is not a literal, and nothing for a group without a title, as Playwright's `test.describe(() => {…})`.

GUT tests in `test_*.gd` files:

```gdscript
# Verifies: FR-GODOT-06/AC1
func test_variable_lookup_is_scope_aware():
```

**Skipped tests.** A test declared with `skip`, `todo`, `fixme`, or `fail` (`fails` in Vitest), or with Vitest's option `skip`, `todo`, or `fails` set to `true` (as in `test("…", { skip: true }, …)`), or inside a group declared so whatever its title (as in `describe.skip.each`), does not count: it never runs, or it passes only while the behaviour is wrong. Nor does a test in which Playwright's `test.skip()`, `test.fixme()`, or `test.fail()` is called without arguments or with the condition `true`, as in `test.skip(true, "…")` (in its body, a hook, or a step), or a test inside a group or file in which one is. Nor does a Go test or subtest whose body calls `t.Skip`, `t.Skipf`, or `t.SkipNow` as one of its own statements (not inside an `if`, a loop, or a function literal), as in `t.Skip("flaky")`, or a subtest inside one.

A test skipped in any other way still counts, because the report does not run the code that skips it: `t.Skip` under a condition, as in `if testing.Short() { t.Skip() }`, or in a helper function; GUT's `pending`, and a GUT script that defines `should_skip_script` or sets `skip_script`; Vitest's `skipIf` and `runIf`, and an option set to anything but `true` (as in `{ skip: isCI }`); Playwright's `test.skip()`, `test.fixme()`, or `test.fail()` called with any other condition, as in `test.skip(isMobile, "…")`; and a Go build constraint that CI does not satisfy, as `//go:build integration`. So do not tag a test that CI skips.

**How the report reads the code.** It parses Go files and reads TypeScript, JavaScript, and GDScript files token by token, so a comment marker in a string is never taken for a comment, and a group's tests are the declarations inside its call. It cannot read JSX text that holds a quote, a backtick, `//`, `/*`, or a parenthesis without its partner, as in `<li>a) first</li>`. When that leaves a parenthesis it cannot pair, or a template literal or block comment it cannot close, in a test file that contains `Verifies:`, it fails and says so. It fails the same way on a GDScript multi-line string that never closes. Directories named `testdata`, `node_modules`, `vendor`, `dist`, or `coverage`, and hidden directories, are not scanned, and neither are Go files that the go tool ignores, whose name or directory name starts with `_` or `.`.

**When the report fails.** It fails on a `Verifies:` comment that names an unknown requirement or criterion, names a requirement without a criterion, has an entry that is not an ID (or an empty one, after an extra comma), names an ID twice for one test, is written in a block comment (or a GDScript multi-line string), is outside a test file, or is not directly above a test the report can name (a group is not one). It also fails on a Go file it cannot parse. In a test file, it also fails on:

- A `Verifies:` comment written after code on any line.
- A line comment that is meant as one but is not spelled `Verifies:`, such as `// verifies: FR-EDIT-02/AC3`, `// Verifies FR-EDIT-02/AC3`, `// Verifies — FR-EDIT-02/AC3`, a list item such as `// - Verifies: FR-EDIT-02/AC3`, or a typo such as `// Verifes: FR-EDIT-02/AC3`.
- A `Verifies:` comment above a commented-out test, as when a test is commented out but its tag is not: a comment line below the tag that starts with a test or group declaration, such as `// func TestOld(t *testing.T) {` or `// it("old", () => {`. The tag would otherwise belong to the test below the commented-out one. Comment out the tag with the test, or move it. A comment that mentions a declaration after other words, as in `// Each case runs in t.Run(…)`, is prose.
- A comment line that continues the ID list of the `Verifies:` line above it, such as `// and NFR-PERF-01`; start that line with `Verifies:` too. That includes a line that holds nothing but IDs and the commas or `and` between them, written as a list item or not, among the comment lines directly above a test or a group or around a `Verifies:` line, as where gofmt moves an indented continuation of a doc comment below a blank comment line.

[`docs/configuration.md`](docs/configuration.md) is generated from the key declarations in `server/internal/config/keys.go`, and `go test ./...` fails when it is out of date. After you add or change a configuration key, regenerate it by running `go test ./internal/config -run TestReference -update` in `server/`.

[`docs/error-codes.md`](docs/error-codes.md) is generated the same way, from the registry of error codes in `server/internal/api/errors.go`. After you add or change an error code, regenerate it by running `go test ./internal/api -run TestReference -update` in `server/`.

## Strings and translations

Every user-facing string is a message in a catalog, with a stable key, in ICU MessageFormat (PRD FR-I18N-01). English is the source language: its catalog has every message, and a translation that lacks one shows it in English.

| Catalog | Formatted by | Messages |
| --- | --- | --- |
| [`web/shared/i18n/`](web/shared/i18n/) | i18next with i18next-icu (`@storycreep/shared/i18n`) | The web app's and the public site's. |
| [`server/internal/i18n/catalog/`](server/internal/i18n/catalog/) | The server's own formatter (`server/internal/i18n`) | The server's: the messages of the API's errors, and later its emails. |

Each catalog is a directory with one JSON file per locale, named after its BCP 47 tag, as `en.json`, which holds the messages by key. Name a key after where the message is used, in names of letters, digits, `_`, and `-`, separated by dots, as `error.not_found`.

- **Web.** Show a message with i18next's `t`, called with the key as a string literal, as in `t("board.empty")` or `t("files.count", { count })`, or with react-i18next's `<Trans i18nKey="…">`. Do not name an argument after one of the options that i18next reads itself, such as `lng` or `ns`. `createI18n` makes an i18next instance in a locale, and `resolveLocale` picks the locale: the user's preference, then the browser's languages, then the instance's default, then English (FR-I18N-02). `formatNumber`, `formatDate`, `formatDateTime`, and `formatRelativeTime` format the rest for a locale.
- **Server.** Name a message with `i18n.K("error.not_found")`, with a string literal, in an `i18n.Message` with its arguments, and format it with the request's localizer, `i18n.FromContext`. The API negotiates each request's locale from its `Accept-Language` and `STORYCREEP_DEFAULT_LOCALE`, writes the error envelope's `message` in it, and names it in the `Content-Language` header. The server formats a subset of ICU MessageFormat, which `server/internal/i18n/messageformat.go` lists: arguments, numbers, plurals, selectordinals, and selects, but no dates or times yet. A catalog with anything else does not load, and the server's tests fail.

The vectors in [`schema/i18n/`](schema/i18n/) hold the two formatters to the same output for the same message, so that a translator writes one dialect of ICU for both.

**Extraction.** `pnpm i18n:extract` reads the keys that the code uses, in Go, TypeScript, JavaScript, and the site's Astro components, and rewrites the catalogs to hold exactly those keys, sorted (FR-I18N-01 AC3). The source catalog gains an empty message for a key it lacks, which it reports until you write the message, and every catalog loses the keys that the code no longer uses. It reads a key only from a call with a string literal, and reports any other call of `t` or `i18n.K`, such as one with a variable. While it cannot read every key, as then or when a file does not parse, it rewrites none of that code's catalogs, so that no message of a key it missed is deleted. `go test ./...` fails when a catalog is not as extraction writes it, and `pnpm test` when a web catalog's message does not parse, or a translation uses an argument that its English message does not.

**The lint rule.** A Biome plugin, [`web/shared/lint/hardcoded-text.grit`](web/shared/lint/hardcoded-text.grit), reports text written in the web's source instead of the catalog, and `pnpm check` runs it (FR-I18N-01 AC1): JSX text with a letter in it, a string shown as a JSX child, as in `{"Save"}` or `{done ? "Saved" : t("x")}`, and the value of an attribute that people read, such as `title`, `alt`, `aria-label`, or `placeholder`. Biome reads only the frontmatter of an Astro component, so the rule does not see the text of its template, which a review of the site's pages has to catch. Mark text that is rightly not translated, such as the product's name, with a comment that says why: `{/* biome-ignore lint/plugin: the product's name */}`.

## The web app

[`web/app`](web/app) is the editor (PRD §10.6): Vite and React, TanStack Router, whose routes are the files of `web/app/src/routes`, TanStack Query for the server's state, Tailwind CSS v4, whose theme is the design tokens of [`web/shared/src/tokens/tokens.css`](web/shared/src/tokens/tokens.css), and Radix UI's primitives, with components of its own. Its strings are messages of the catalog (see [Strings and translations](#strings-and-translations)).

- **Running it.** `pnpm --filter @storycreep/app dev` serves the app at <http://localhost:5173/app/>, as it changes, and passes the API's requests to the server at <http://localhost:8080>, run as [`deploy/README.md`](deploy/README.md#development) describes, or at the URL in `STORYCREEP_DEV_API_URL`. The router's plugin writes `web/app/src/routeTree.gen.ts` from the routes' files as it runs, and as the app builds: commit it with them.
- **The server's copy.** `pnpm build` writes the app's build to `server/internal/webassets/dist/app`, which a binary built with `-tags webdist` embeds, as the image's does (`deploy/Dockerfile`). A binary built without the tag, as by `go test`, serves a page that says it has no editor, so the Go toolchain alone builds and tests the server. The server answers every path under `/app/` that is neither a file of the build nor names one, by an extension in its last segment, with the app's entry page, so that the router shows it: a route's path never ends in an extension, nor in a parameter whose value may have a dot in it, as a file's name. `/app/index.html` redirects to `/app/`. It serves the files under `assets/`, whose names Vite writes with a hash of their content, for a year, which is why the build refuses a `web/app/public/assets/` directory, whose files Vite would copy there with their names as they are; each file has the type of its extension in `fileTypes` (`server/internal/httpserver/pages.go`), or `application/octet-stream` for one that it lacks, which `go test` refuses of a file of the app's build, once the app is built, as CI builds it first, and those that compress, as scripts and stylesheets, as gzip to a browser that accepts it. Vite inlines no file as a `data:` URL, which the policy below would refuse.
- **Content-Security-Policy.** The entry page's policy allows the page's own scripts and styles, and those with the response's nonce, which the server writes into the page in place of `__STORYCREEP_CSP_NONCE__` (PRD NFR-SEC-09); nothing else inline. React's `style` props are set through the DOM, which the policy allows, but a library that adds a `<style>` or a `<script>` element to the page needs the nonce: `main.tsx` gives it to `get-nonce`, which Radix's dialogs read, and gives another library it from `cspNonce` alike. The end-to-end tests fail on a violation of the policy on any page that they open, as `test` in `shell.spec.ts` watches for.
- **Requests.** The app calls the server only through the API client of `@storycreep/shared/api` (`api` in `web/app/src/api.ts`), whose types are generated from the OpenAPI document (see [The API contract](#the-api-contract)), so that it describes no request or answer by hand (PRD FR-API-02 AC2). A list that the server answers a page at a time, from a cursor, is read with `pagedQuery`, which asks for the next page as the user does. A query that the server counts among the requests about credentials, whose limits signing in and changing the password share (PRD FR-AUTH-05), as the API tokens' list or an invitation's lookup, has the options of `askedSparingly`, so that the page asks for it again at most once a minute, whether the server answered or refused it, as a component that reads it mounts again or the tab is shown again, and once it knows that the answer has changed, but a list of which it shows more than the first page only then, from its first page, since each page is a request of its own, and does not try again at once what the server failed to answer itself, as with 500, which it counted too; a request that did not reach the server, as one that no answer came to, is tried and asked for again as any query's is. A Biome plugin, [`web/app/lint/direct-request.grit`](web/app/lint/direct-request.grit), reports `fetch`, `XMLHttpRequest`, `EventSource`, `WebSocket`, and `sendBeacon` in the app's source, but its tests, named as globals, in an object's shorthand too, as `{ fetch }`, or as properties, destructured too; it reads names, not values, so one that a script computes, as `Reflect.get(globalThis, "fetch")`, is for review to catch. Code that rightly makes such a request, as the real-time channel's socket does (`web/app/src/document/realtime.ts`), is marked with a comment that says why, as `// biome-ignore lint/plugin: the real-time channel's socket`.
- **Hover.** A touch screen has no hover, so no control may depend on it (PRD FR-EDIT-09): a hover state changes how a control looks, never whether it is shown, where it is, or how large. The build fails on a CSS rule that applies on hover, whose selector mentions `:hover` anywhere, or that is nested in such a rule, or in a `@scope` whose bounds mention it, and sets a property that `hoverProperties` in [`web/app/lint/hover.ts`](web/app/lint/hover.ts) does not list: colours, a text's decoration, `box-shadow`, and `cursor`, and no custom property, which may feed any other. Tailwind's `hover:` utilities that set only those, as `hover:bg-surface-hover`, `hover:text-accent-hover`, or `hover:underline`, pass, and `hover:opacity-100`, `hover:block`, `hover:scale-105`, or `hover:bg-[url(…)]` do not, nor do `hover:shadow-md` and `hover:ring-2`, which set Tailwind's custom properties: write a shadow on hover as `hover:[box-shadow:…]`. Show what hover would reveal all the time, or on focus, selection, or a tap, rather than on hover. A property joins the list only if it cannot show, hide, move, or resize what it styles. The check cannot tell a colour that tints a control from one that makes it visible, as from `transparent`, so never make a control transparent, or the colour of what is behind it, until hover. The build fails, too, on CSS that lightningcss, which the check reads the build with, cannot read, as a selector or an at-rule newer than it, since a rule there could apply on hover unchecked. It reads the stylesheets that Vite writes, the `<style>` elements of `index.html`, and the stylesheets of `public/`, which Vite copies as they are, and fails on CSS that a script imports as a string, with `?inline` or `?raw`, which goes into the script, where it cannot read it: import a stylesheet as one. CSS that a script writes itself is for review.
- **Colours.** The theme has only the tokens' colours, named for their use, as `bg-surface` or `text-fg-muted`, each with a light and a dark value, which follow the system's mode. `tokens.test.ts` holds the pairs that are shown together to the contrast of PRD NFR-A11Y-06 in both modes, so a pair that a component shows that it does not list joins its lists, and a new colour is written as `light-dark(#rrggbb, #rrggbb)`, which it reads.
- **Sessions.** The page's session is `sessionQuery` (`web/app/src/api.ts`), null while it is signed out, and the account is `accountQuery`, which the root route reads before any page shows, with the instance (`instanceQuery`), whose locale it applies (`applyLocale`), and again once the account changes while the page stays, as on signing in on the invitation's page, and which sends every page to first-run setup while it is pending, and signs the page out if the account is answered with 401 `unauthenticated`, as of a session revoked since the session was read. ## The API contract

The server's OpenAPI 3.1 document is generated from its huma operations (PRD FR-API-02), served at `/api/v1/openapi.json`, and committed as [`schema/api/v1/openapi.json`](schema/api/v1/openapi.json). The TypeScript types in `web/shared/src/api/v1.gen.ts` are generated from it, and the client in `web/shared/src/api` is typed by them, so nothing describes a request or a response by hand. `go test ./...` fails when either file is out of date, or when a route of the API is not in the document (FR-API-02 AC1). After you add or change an operation, regenerate both by running `go test ./internal/httpserver -run TestOpenAPIDocument -update` in `server/`.

- Register every operation with `api.Register`, which documents the error envelope as its default response. A test provokes errors from every route, and checks that each answer is the envelope that the document describes (FR-API-04 AC1). A route that none of its requests makes fail fails the test, which then needs a request of its own for it.
- `server/internal/apicontract` reads the document. It refuses a keyword or an object of OpenAPI that it does not know, and a keyword beside a `$ref` other than one that only annotates it, which is where huma writes the tags of a field whose type is a struct, such as `default` or `minProperties`. That way nothing in the document escapes the compatibility check. It also refuses a `discriminator`, which huma's validator (v2.39.1) mishandles: at each object of a body without the discriminator's property, or whose property is neither a string nor `null`, it adds a segment to the location of every later problem of the body, so that a body of many such objects costs memory that grows with the square of their number, and one of 5 MiB runs the server out of memory. Teach the package discriminators only once huma pops the segment that it pushes. The TypeScript generator refuses what the client cannot express yet, such as a parameter that is not a string, number, or boolean, or a body that is neither JSON nor a file. A body that is a file, whose media types are all binary strings, as an upload's is, is a `Blob`, which the client sends as it is, and an operation that answers with one has `blob` set in the generated `routes`, so that the client reads its answers as a `Blob`. When a change needs something else, teach the package the new case.

`pnpm api:check` compares the document with the one on the main branch, as CI does for every pull request, and fails on a change that breaks a client of `v1` (FR-API-01 AC3). Every request that `v1` accepted must still be accepted, and a response may hold only what `v1` said it would, except that it may gain properties and headers, which clients ignore, and errors may gain statuses, because every error has the envelope. An operation that took neither `If-None-Match` nor `If-Modified-Since` may also gain a 304, which only a request with one of them gets, as when it starts sending an `ETag`. Clients fail on enum values that they do not know, so a value added to a response's enum breaks them. A request's `oneOf` or `anyOf` whose members all refer to named schemas may gain members, as the command endpoint's union does when you register a type of command, but a member that a `oneOf` gains must take no value that another member took, because a value that two members of a `oneOf` take is refused: give it a property that every member requires, with values of its own, as a command's `type`. A response's may lose members, but not gain them. `Breaking` in `server/internal/apicontract/compat.go` lists the rules.

Until the first release, no client depends on `v1`, so a pull request may break it if it says why. Add an `API-Break` trailer to the message of one of its commits, in the last paragraph, with any other trailers:

```text
Remove the commit field from /version

API-Break: nothing reads it, and no client depends on v1 before the first release
```

The check then lists the changes with the reason, and passes. From the first release, plan item 119 compares the document with the release's, and a breaking change needs a new version prefix, `/api/v2`.

## Database migrations

The migrations are SQL files in `server/internal/database/migrations/`, embedded in the binary and applied by [goose](https://github.com/pressly/goose). `storycreep migrate` applies them, as the superuser in `STORYCREEP_DATABASE_ADMIN_URL`, under an advisory lock (PRD FR-ADMIN-04).

- Name a new migration with the next version, as in `00002_workspaces.sql`. Versions count up from `00001` without a gap, and a test fails otherwise. CI tests a pull request merged with the main branch, so if another pull request that adds the same version is merged first, yours fails when its checks run again, and you renumber yours. Before you merge a pull request that adds a migration, run its checks again if the main branch has gained a migration since they last ran: once two migrations with one version are both on the main branch, neither can be renumbered, because a merged migration is never renamed.
- Migrations are forward-only: start the file with `-- +goose Up` and write no `-- +goose Down` section. Each migration runs in its own transaction, so that a failed one leaves no trace, and a test fails on `-- +goose NO TRANSACTION`. A migration is the same on every server, so a test also fails on `-- +goose ENVSUB ON`, which would fill it in from the environment.
- A migration on the main branch is never changed, deleted, or renamed, because no database that applied it would apply the new version. `pnpm migrations:check` fails a branch that does, and CI runs it on every pull request. To change the schema again, add a new migration.
- The superuser that runs the migrations owns the tables, which are in the `public` schema: migrations run with `search_path` set to `public` alone, whatever the admin URL, the login, or the database sets. Grant the server's privileges to the `storycreep_app` role in the migration that creates a table; the server's login has no other privileges, besides `CONNECT` on its database, which migrating grants it.
- A table whose rows belong to a workspace is a tenant table (PRD §5.4, NFR-SEC-01). Give it a non-null `workspace_id` with a foreign key to `workspace` and an index that starts with it, enable and force row-level security, and give it the `workspace_isolation` policy that `00004_tenancy.sql` gives the others. Grant `storycreep_maintenance` `SELECT` on it, as that migration does on the others, because the maintenance jobs read across workspaces. A row that refers to another row of its workspace does so through a foreign key that includes `workspace_id`, so that it cannot refer to another workspace's row. Then add the table to `Tables` in `server/internal/database/isolationtest`, with how to add a row, so that `TestTenantIsolation` tries to read, change, and add its rows from another workspace's transaction. `TestTenantTables` fails on a table that is not a tenant table done this way, unless it is one of the few that span workspaces, which it lists (FR-TEN-01 AC1). Try a repository's own operations with the harness's `Fixture.Check`, which points them at another workspace's rows, as a broken filter would.
- The four functions of the context bootstrap, in `00005_context_bootstrap.sql`, are the only way past row-level security that a request can reach, and the only `SECURITY DEFINER` functions: a test fails on another one, or on one declared in another migration (PRD §5.4).
- The `storycreep_maintenance` role bypasses row-level security, for the closed list of maintenance jobs in PRD §5.4. Only `server/internal/maintenance` may use it: a test fails when another package imports that package, or uses the configuration's `DatabaseMaintenanceURL` or package `database`'s helpers for the maintenance login outside the packages that provision the login. The role may read every tenant table, as above, and the accounts and workspaces; grant it what else a maintenance job needs, such as deleting rows, in the migration that adds the job.
- A view reads its tables with its owner's privileges, and row-level security never holds the superuser that owns it, so the server would see every workspace's rows through it. Create every view `WITH (security_invoker = true)`, so that it reads them with the privileges of whoever queries it, and no materialized view, which row-level security never applies to. A test fails otherwise.
- A table of a project's content whose rows users delete sends them to the project's trash (PRD FR-PROJ-06), where they stay for 30 days before the purge deletes them. Give it a `deleted_at`, which deleting a row to the trash sets and restoring it clears, and a view named `live_` and the table's name, `WITH (security_invoker = true)`, of its columns over its rows whose `deleted_at` is null, through which everything that reads the content reads it, so that nothing in the trash is searched, exported, or published. Grant `storycreep_app` `DELETE` on the table for the purge. Then add its rows to the trash's list (`TrashItems`), if the trash lists them, and to its purge, in `server/internal/database/queries/trash.sql` and package `trash`. A row that belongs to a board, as a board's node or variable, is in the trash with its board: its view leaves out the rows of a board that is in the trash too, as `live_node` and `live_variable` do, its foreign key to the board deletes it with the board's purge, and restoring the board brings back the deleted folders that its rows are in, as package board does for its variables. A row that refers to rows that go to the trash, as a connection to its nodes, is in the trash with any of them alike: its view leaves out the rows whose nodes are in the trash, as `live_connection` does, so that one comes back once none of them is, and its package registers with the pipeline which of its rows a restoration leaves in the trash still (`commands.RegisterReconnection`), which a command that restores a row reports (`Tx.Restored`), and which the batch's answer lists as `not_reconnected` (PRD FR-PROJ-06 AC1), as package connection does. A row that the trash does not list, as a deleted folder, component type, attribute definition, or connection, goes to the trash all the same, with its view and its purge, and is restored by what restoring a listed row brings back, as a component brings back its type (package component). `TestTrashTables` in `server/internal/trash` fails on a table of a project's content with a `deleted_at` that it does not list, and holds each table that it lists to its view, its place in the list, and its purge. A view keeps the columns that its table had when it was created, so a migration that adds a column to such a table creates its view again, with `CREATE OR REPLACE VIEW … WITH (security_invoker = true)`: the test fails until it does. Repeat the `WITH` clause, because `CREATE OR REPLACE VIEW` replaces the view's options with those that it names, and one without it would read the table as the superuser that owns the view, every workspace's rows with it.
- After you change a migration or a query in `server/internal/database/queries/`, run `go generate ./internal/database` in `server/` to regenerate the code that sqlc builds from them.
- The job queue's tables belong to [River](https://riverqueue.com), and come from River's own migrations, copied into ours (`00002_river_2_to_4.sql` and `00003_river_5_to_8.sql`, which say how). When you upgrade River and it adds a migration, copy the migration into a new migration of ours in the same way, and grant `storycreep_app` the privileges on any table it creates. `TestRiverSchema` in `server/internal/jobs` fails until the schema our migrations build is the one River's migrator builds, and `TestRiverPrivileges` until the grants are there.

Database tests get their own database from `dbtest.New(t)`, in `server/internal/database/dbtest`, which copies a template with the migrations applied, and connect to it as the superuser (`AdminURL`), the application login (`AppURL`), or the maintenance login (`MaintenanceURL`). A package whose tests use it runs them with `os.Exit(dbtest.Run(m))` in its `TestMain`, which keeps the libpq environment variables out of the tests and removes the PostgreSQL container when they are done. The tests of the S3 driver get a bucket of their own from `blobtest.S3(t)`, in `server/internal/blob/blobtest`, which starts MinIO once per test binary, as `dbtest` starts PostgreSQL, and skips the test with `-short`; a package whose tests use it calls `blobtest.Stop()` from its `TestMain` once they are done. MinIO no longer publishes images, so it runs `pgsty/minio`, a build of its community edition, pinned to a release, unless `STORYCREEP_TEST_MINIO_IMAGE` names another. Every store passes the same suite, `blobtest.Suite`, which a new driver runs too (PRD FR-ASSET-01 AC1). For the database, two environment variables configure it: `STORYCREEP_TEST_POSTGRES_IMAGE` picks the image (the default is `postgres:17-alpine`), and `STORYCREEP_TEST_UPGRADE_FROM` names, as an absolute path, a directory of older migrations that the template is migrated with first. CI's upgrade test sets it to the main branch's migrations and runs the whole suite on the upgraded database (FR-ADMIN-04 AC2).

## Conventions

- Text files use LF line endings everywhere. `.gitattributes` enforces this, and `.editorconfig` sets the indentation: two spaces, except tabs for Go and GDScript.
- Every user-facing string is a message in a catalog (see [Strings and translations](#strings-and-translations)), and every new endpoint is in the OpenAPI document. The plan's standing checklist lists the rest.
- Register every route with `api.Register`, or `Mux.Handle` for a handler that is not a huma operation, or `Mux.HandlePage` for a page of the web interface, which the OpenAPI document leaves out, in `server/internal/api`, which records the capability the route requires. A test walks the routers and fails on a route that declares none (PRD NFR-SEC-02). A route that needs a signed-in user declares either the scope that an API token must hold to use it, with `api.TokenScope`, or that it takes a session alone, with `api.SessionOnly`, and `api.Register` panics on one that declares neither (FR-AUTH-04 AC6). FR-AUTH-04 lists the session-only endpoints: the account and its credentials, and the administration of the workspace and the instance; a route of content or of releases takes a token, and `TestRouteClassification` lists the routes that do, with their scopes. The handler of a route that takes a token passes the request's actor, with its token, to the service, which answers a workspace or a project that the token does not cover, of another workspace or other than the one that it is narrowed to, with 404 (`scope.Token`), and lists only what the token covers; a session-only route answers a token with 403 `session_required`, and its description says so (`sessionAuthDoc`). `TestTokenScopes` and `TestEveryRouteReachable` walk the routes that take a token, and `TestTokenNarrowedToProject` tries each with a token of another workspace and one narrowed to another project, which must be answered with 404.
- Every route of the API, under `/api/`, counts its requests in a rate limit (PRD FR-API-04, NFR-SEC-06): `api.Register` counts a GET in the `read` bucket and any other method in `write`, unless the route names its bucket with `api.RateLimit`, as `api.BucketAuth` for signing in and the other requests about credentials, making, listing, and revoking API tokens among them, in which `api.Register` refuses a route that takes a token, so that a token's requests cannot use up its owner's limit of revoking it, and `api.BucketExport` for an export. The limit counts after the route's own guards, and before the middleware that the route names with `api.AfterLimit`, which is for middleware that may keep a request waiting, as an upload's wait for one of a few slots, so that a request that the limit refuses does not wait first, and `api.Register` appends the limit to the route's description and documents the RateLimit headers on its responses. The description of a route of `api.BucketAuth` says what its limit is with `authLimitDoc` (`server/internal/httpserver/ratelimit.go`), which names every such route, and `TestEveryRouteRateLimited` lists them, so a route that joins or leaves the bucket changes both. Only a public route outside `/api/` that answers without the database, as the health probes, may say `api.Unlimited`. `TestEveryRouteRateLimited` checks that every route is counted, and is refused over its limit with 429.
- A handler decodes the request, calls a service, and encodes the answer. The service checks the role, with `server/internal/authz`, which holds the permission matrix of PRD §5.6, and reads and writes the database (FR-TEN-03 AC2). A test fails on a handler, in `server/internal/httpserver` or `server/internal/api`, that imports the queries or `authz`, opens a transaction, writes, enqueues a job, compares roles (with `AtLeast`, or with `==`, `!=`, or a `switch` against a constant of `server/internal/role`), or records an audit entry. A new operation of §5.6 adds its row to the matrix and to `TestPermissionMatrix`, which fails until every operation of the matrix has one, and through which an operation of the workspace joins `TestGrantAuthorizesNoWorkspaceOperation`, which checks that a project grant authorises none of them (FR-TEN-04 AC4); mark an operation that is a route of a project that it adds with `project`. A new route of a workspace or a project joins `TestViewerReadsOnly` and `TestNoRoleNotFound`, which fail until they know the route's capability and parameters.
- A handler reports an error by returning an `*api.Error` with a code from the registry, which the client receives in the error envelope. Any other error is answered with `internal_error`, and logged with the request ID, so its text never reaches the client.
- Outside tests, only `server/internal/config` reads the environment or knows the deployment mode (`STORYCREEP_MODE`). Code that behaves differently in the two modes reads `config.Capabilities`. A test fails on non-test code in any other package that reads an environment variable, names `STORYCREEP_MODE`, or uses a mode value (PRD FR-ADMIN-01 AC3). Test files are exempt, because they set the mode up, and so are test-support packages: a package whose name ends in `test`, such as `dbtest`, and that only test files and other test-support packages import, so that it is not part of the binary.
- Secrets are held as `secret.Value` (`server/internal/secret`), which prints, logs, and encodes as `[REDACTED]`. Call `Reveal` only where the secret is used.
- Background work is a job of the queue in `server/internal/jobs` (PRD FR-JOBS-01). Register the worker of a kind of job with `jobs.Register`, and enqueue a job with `Queue.Enqueue` in the transaction of the change that needs it, so that the job runs only if the change commits. A kind whose work takes much of the process's memory, as decoding an image does, is made serial with `jobs.Serial`, which runs its jobs one at a time in a process, on a queue of their own, rather than holding the other kinds' workers while they wait for their turn. The queue's tables span workspaces and have no row-level security, so a job's arguments hold identifiers, never content, and its work reads and writes a workspace's rows in a transaction of that workspace, on the workers' pool that the job carries (`job.DB.InTx`). A job can run more than once, as when the instance running it is killed, so its work must be safe to repeat. When the server stops, it cancels the context of the jobs that have not finished in time, and a job whose work returns that context's error, or wraps it with `%w`, is attempted again without the attempt counting.
- Record each security- or tenancy-relevant event (PRD FR-TEN-07) with `audit.Record` (`server/internal/audit`), in the transaction of the change that it records, so that the entry commits only with the change. Register a new event's action in `server/internal/audit/events.go`, with whether it belongs to a workspace, the kind of entity that it is about, its results, and its metadata keys, which `Record` holds entries to, and record it in the pull request that adds the feature, with a test that produces it (FR-TEN-07 AC2). An entry names people by ID only, never by email address or display name (§9.6). An event that belongs to no workspace, such as a login, is recorded in a transaction without one, and an event that is a refusal, such as a failed login, changes nothing else, so its transaction still commits.

The messages' JSON Schema, [`schema/realtime/v1/messages.schema.json`](schema/realtime/v1/messages.schema.json), is generated from the package's types: after you change them, run `go test ./internal/realtime -run TestSchemaFile -update` in `server/`. A field that a server's message gains, which a client ignores, keeps the version; a change that a client could not ignore is a version of its own. A route that upgrades to a WebSocket joins `upgradeRoutes` in `server/internal/httpserver`, whose walks of the routes take its 426 `upgrade_required` for reached, since their ResponseRecorder cannot be upgraded, and refuses a socket of the session cookie from a page of another origin (`sameOrigin`), since a browser sends the cookie with a WebSocket of any page, as `refuseCrossSite` lets a GET through. A socket's credential and its user's access to a project are checked again before each page of operations that it is sent, so a read that the hub adds goes through the same checks (`Hub.read`).
- A project's draft is validated by [`server/internal/validation`](server/internal/validation) (PRD FR-DEP-03, plan note N55), whose rules are pure functions of what one read of the draft as of one moment gives (`validation.Run`), so that publishing validates, in its build's own transaction, the draft that it serialises (FR-DEP-04), and `GET /api/v1/projects/{id}/validation` answers with the report, one document rather than a paged list. A new rule is a code of the table in `validation.go`, with its severity, the kind of entity that its findings are about, and its message in the server's catalog (`validation.<code>`), a value of the `enum` tag of `Finding.Code`, a line of PRD FR-DEP-03's table, and a fixture that it finds something in and one that it finds nothing in, in `ruleCases`, which `TestRules` fails without. A warning or an info about a kind of entity is a code that a mute may silence (`validation.Mutable`), which the database's check of `validation_mute`'s codes names too (migration 00028), as do the `enum` tags of the code of the payloads of `validation.mute` and `validation.unmute`, so a new one changes that check in a migration of its own, and those tags; `TestCodeEnums` fails on a tag that lacks a code, and `TestValidationMuteCodes` on a check that does. A new field that refers to another entity by its ID, as a speaker or an entry node does, joins the read of the draft (`load`), which reads each kind of row once, and `ref_dangling`. A mute is part of its owner, as an expression is: a new kind of entity that a warning is about gains a column of `validation_mute`, with a foreign key that deletes the mute with it, a case of `MuteOwnerLive` and `TouchMuteOwner`, and an owner of its kind in `TestValidationMuteCodes`; the commands `validation.mute` and `validation.unmute` touch the kinds that a warning or an info is about, which `validation.MuteOwners` reads of the rules.
- The reference fixtures of PRD §9.1, `small`, `medium`, `large`, and `dense`, are generated by [`server/internal/fixture`](server/internal/fixture) from a seed, as batches of commands (NFR-Q-06, plan note N52), and `go run ./cmd/fixturegen` in `server/` loads one into a new project of a running instance through the API, with an API token, for manual testing. A seed gives the same batches on every platform, which `TestGenerateReproducible` checks against a digest of each size's: a change of the generator changes every benchmark's project, so update the digests only on purpose, and say so in the pull request. A server metric of §9.1 is a Go benchmark of a project of a fixture, `large` unless its target names another, edited through the API as the web app edits it, which reports its target's statistic with `b.ReportMetric`, as `p95-ms`, fails with `b.Errorf` over its target, and is tagged with its `NFR-PERF-…`, as `BenchmarkCommandRoundTrip` in `server/internal/httpserver` is. A benchmark's batches each change what they name, since the server makes a no-op of one that changes nothing, and `dbtest` gives a test binary's benchmarks a PostgreSQL server of their own that keeps what it commits, as a production server does, where the tests' does not; a benchmark has a database of its own, a copy of the one that its test binary loaded the fixture into once and froze (`newBenchServer`, `dbtest.Frozen`), so that a run loads `large`, which takes minutes, once however many benchmarks it has, and it vacuums, analyzes, and checkpoints its copy, and reads it into PostgreSQL's buffers (`pg_prewarm`), before it times anything. CI's benchmark job runs every benchmark of the base and of the change, in turn, four times each, on one runner, in the order base, change, change, base, twice, each run a go test of its own that is one sample of each metric, and `cmd/benchgate` fails the build where a metric whose unit is a time, `ns/op` or one that ends in `-ms` or `-ns`, has a median more than 20% above the base's, and a Mann-Whitney U test of the runs finds the two apart at p < 0.05.
- Every table with a `project_id` column has a foreign key, with its `workspace_id`, to `project (workspace_id, id)` with `ON DELETE CASCADE`, so that the purge of a project whose time in the trash has passed deletes every row of it (PRD FR-PROJ-01 AC3). `TestProjectTables` in `server/internal/database` fails on a table without one.
- The plans of the hosted service, their limits, and their feature flags live in one file, [`server/internal/entitlements/plans.json`](server/internal/entitlements/plans.json), which the server embeds and the pricing page reads (PRD FR-ENT-01). Its numbers are placeholders until the hosted service's prices are set, so no code or test names them: a test reads them from the file. A change that adds to a workspace's usage of a limit checks it once, with `entitlements.Check` in its transaction, at the limit's one enforcement site, which has a test that reaches the limit (FR-ENT-01 AC1). Code that would only lead to such a change asks that site, never `entitlements.Check` itself, as registering with a link invitation's link, which leads to a membership, asks the members limit's (`workspace.Service.CheckRoom`) before it adds the account, and again in the account's transaction. The route of either answers the `*entitlements.LimitError` with `limitExceededError` (`server/internal/httpserver/entitlements.go`), which is 409 `limit_exceeded` with the limit's key, usage, and limit (FR-ENT-03 AC1). A limit that the plan file marks `inert_until` is checked by no code until the requirement that it names.
- A workspace's usage of the things that the plans meter (PRD FR-ENT-02) is kept by [`server/internal/usage`](server/internal/usage): a change records what it adds to a key, or takes from it, with `usage.Record` in its own transaction (a command, with `Tx.AddUsage`, or with `Tx.AddUsageOnceApplied` for what depends on the batch's later commands, as the boards that a project's deletion takes, and its restoration adds back, which is all that a batch of the project in the trash adds to them), as a row of `usage_delta`, and never updates a counter, which only the rollup job writes. `entitlements.Check` reads the usage through `usage.Meter` when the limit is a number, and the meter holds a lock of the workspace's key until the transaction ends for the keys counted exactly, so the check and the delta belong in one transaction. The pull request that first records a key's deltas also registers the key's recount in `drifts` (`server/internal/usage/jobs.go`), with a query that counts its rows, so that the reconciliation job corrects its drift. A key that no rows but its deltas record, as `api_requests`, the requests of a workspace's API tokens, which package apitoken records as it accepts each, has no recount. A delta of a key that is counted approximately, in a transaction that writes nothing else that must outlive a crash of the database, may be recorded with `usage.RecordUnflushed`, whose transaction then commits without waiting for the disk, as package apitoken records the requests, so that none of them waits for it.
