# Rich text

The rich text of a project's content, node bodies, connection labels, and component descriptions, is a ProseMirror document of a constrained schema, stored as JSON (PRD FR-TEXT-01, ADR-020, plan note N40). The schema's nodes and marks are TipTap's, so that the editor's extensions, with only the attributes that the table below gives them, write the documents that the server stores. ProseMirror writes every attribute of a node, `null` when it is not set, as a value reference's `decimals`; the editor leaves such an attribute out before it sends a document, since the server refuses a `null` wherever it is in a document.

| File | Contents |
| --- | --- |
| [`v1/rich-text.schema.json`](v1/rich-text.schema.json) | The JSON Schema of a document, version 1, with examples. Its `$id` is the URL of the file on the main branch. `server/internal/richtext` generates it, and `go test ./...` fails when it is out of date; `go test ./internal/richtext -run TestSchemaFile -update`, in `server/`, rewrites it. It is shaped so that a validator's work grows with a document's size, whatever the document holds: of the branches of each `oneOf`, only one holds blocks, so both kinds of list are one definition, `list`, and no array is `uniqueItems`. It has only the keywords that the API's OpenAPI tooling reads, since the API's document holds it for a field of rich text, so it has no `not`, and no `oneOf` beside an object's properties, which a bulleted list's lack of `attrs` would need. The API's document holds it without a `discriminator` beside its `oneOf`s, an OpenAPI keyword that JSON Schema does not have (see Errors, below). |
| [`vectors.json`](vectors.json) | The test vectors of the validation and of the derivations below. The Go package `server/internal/richtext` runs every vector, and so will the TypeScript client, the editor's validation (plan item 57) and the play mode's segments (item 71), so that the implementations cannot drift apart. |

## The document

| Node | Fields | Holds |
| --- | --- | --- |
| `doc` | `content` | At least one block: `paragraph`, `bulletList`, or `orderedList`. The editor's empty document is one empty paragraph. |
| `paragraph` | `content`, optional | Inline nodes: `text`, `hardBreak`, `mention`, and `valueRef`. |
| `bulletList` | `content` | At least one `listItem`. |
| `orderedList` | `attrs.start`, optional, from 0 to 999,999, 1 when it is not given; `content` | At least one `listItem`. |
| `listItem` | `content` | A `paragraph`, then any blocks. |
| `text` | `text`, at least one character; `marks`, optional | Text, without a control character (Unicode's `Cc`) but a tab, a bidirectional control (`Bidi_Control`, as U+202E RIGHT-TO-LEFT OVERRIDE, which reverses the text after it, or U+200F RIGHT-TO-LEFT MARK), or a line or paragraph separator (U+2028, U+2029): a line break is a `hardBreak`, and a paragraph a `paragraph`. These are the characters that the other texts that people enter in Storycreep, as a project's description, may not hold, but for a line feed, so that no text changes how the text around it shows, as a node's preview beside its title; the editor takes them out of text that is pasted before it sends a document. A tab, which ProseMirror keeps in text that is pasted as plain text, is white space, as a space is. |
| `hardBreak` | `marks`, optional | A line break within a paragraph. |
| `mention` | `attrs.id`; `marks`, optional | A component (`cmp_…`), which the text shows by its name (FR-TEXT-03). |
| `valueRef` | `attrs.ref`, `attrs.attribute`, `attrs.decimals`; `marks`, optional | A value, which the text shows as the runtime renders it (FR-TEXT-02): a variable's (`ref` is a `var_…`, and there is no `attribute`), or a component's runtime attribute's (`ref` is a `cmp_…` and `attribute` the attribute definition's `atr_…`). `decimals`, from 0 to 6, shows a number with that many digits after the point, rounded half away from zero (PRD §5.8.9); a value that is not a number is shown as it is. |

The marks are `bold`, `italic`, `strike`, `code`, and `link`, whose `attrs.href` is the URL. A node has each mark at most once, and the code mark with no other, as the editor's code mark excludes the others. Every node and mark is an object with a `type`, and has no field that the table does not give it, so `attrs` on a paragraph or on a bulleted list, or a link's `target`, is refused, and no field is `null`, which is refused with `wrong_type`. An ID is read regardless of case, as [`../ids/README.md`](../ids/README.md) says. A number is read as `JSON.parse` reads it, as the nearest double: `3.0` and `3e0` are 3, and so is `2.99999999999999999999`, which has more digits than a double holds; a number too large for a double, as `1e400`, which `JSON.parse` reads as `Infinity`, is `out_of_range`.

A link has at most 2,048 characters, counted as code points (not as JavaScript's `length` counts them, in UTF-16 code units), none of them white space (Unicode's `White_Space`), a control character (`Cc`), a format character (`Cf`, as U+200B, U+202E, or U+FEFF), or another character that a renderer shows nothing of (`Default_Ignorable_Code_Point`, as U+3164 HANGUL FILLER, a letter, U+034F COMBINING GRAPHEME JOINER, a mark, or a variation selector), which would hide or reorder what a reader sees of it (PRD NFR-SEC-08), and each `%` in it starts an escape, `%` and two hexadecimal digits. Those characters are the same in Unicode 15.0, the version of the server's tables, as in Unicode 17.0. Its scheme, which is read regardless of ASCII case and of no other, is one of these:

- `mailto:`, followed by an address, what is before the first `?`, which is not empty, and then, after that `?`, its query. Each of the query's fields, which `&` separates, is empty, or a name followed by `=` and its value, and the name, read regardless of ASCII case, is `to`, `cc`, `bcc`, `subject`, or `body`, so that no link sets a field, as `attach`, for which a mail client could read a file. A `mailto:` link holds its delimiters only where they delimit, as RFC 6068 has them, since a mail client that reads the fields otherwise than after the first `?` and between the `&`s would read a field that the link does not set: it has no `#`, which RFC 6068 gives it no use for, and after which a client that does not cut a fragment off reads a field, as `attach` in `mailto:keeper@example.com#?attach=/etc/passwd`; no `;`, which HTML 4 and Python's `parse_qs`, before Python 3.9.2, read as an `&`, as in `mailto:keeper@example.com?subject=Light;attach=/etc/passwd`; an address without an `&` or an `=`, as in `mailto:keeper@example.com&attach=/etc/passwd`, where a client that reads a field wherever an `&` is reads `attach`; and fields whose values have no `?` or `=`, as in `mailto:keeper@example.com?subject=Light?attach=/etc/passwd`, where a client that reads the fields after the last `?` reads `attach`. Each of these characters in an address or a value is escaped: `%23`, `%3B`, `%26`, `%3F`, and `%3D`. Each escape is read as the byte that it stands for, with its digits in either case, and those bytes, with the characters between them, are UTF-8, as RFC 6068 has them, in the address and in the value of every field but `body`: a mail client reads bytes that are not UTF-8 as it chooses, as Latin-1, in which `%85` is NEL and `%AD` a soft hyphen, so `mailto:keeper@example.com?subject=Light%85` is refused, as JavaScript's `decodeURIComponent` refuses its subject. The address, and the value of `to`, `cc`, or `bcc`, which name addresses too, escape none of the characters that a link may not hold, above, which would hide or reorder the address that a mail client shows, as U+202E RIGHT-TO-LEFT OVERRIDE (`%E2%80%AE`) has a mail client show `mailto:%E2%80%AEmoc.elpmaxe@evil.example` as `elpmaxe.live@example.com`, or start another header, as a line break does in `mailto:keeper@example.com%0D%0ABcc:evil@example.com`. Once their escapes are read, they are addresses that `,` separates, of which a `to`, `cc`, or `bcc` may have none, each an `addr-spec` as RFC 6068 has it, without a quoted local part, and with a domain that a message can be sent to, as RFC 5321 has it: a local part, one or more atoms that single `.`s separate, an atom being one or more ASCII letters and digits and ``!#$%&'*+-/=?^_`{|}~`` (RFC 5322's `atext`); `@`; and a domain, one or more labels of ASCII letters, digits, and `-` that single `.`s separate, or an address literal of an IP address: `[`, then an IPv4 address as an `http` link's host may be one, below, or `IPv6:`, in any ASCII case, and an IPv6 address as an `http` link's brackets hold one, and `]`, as `[192.0.2.1]` or `[IPv6:2001:db8::1]`. So an address has no display name, comment, group, quotes, or second `@`, which a mail client shows in place of the address that the message goes to, as it shows `mailto:%22support@paypal.com%22%3Cx@evil.example%3E`, whose message goes to `x@evil.example`, as `support@paypal.com`. RFC 6068 takes RFC 5322's atoms in a domain too, of which no other character is in a domain that a message can be sent to, and each of which a mail client could show as what it is not, or read otherwise: `mailto:support@paypal.com%2F.evil.example` would show `support@paypal.com/.evil.example`, which reads as an address at `paypal.com`, and `mailto:x@paypal.com%2540evil.example` an address that a client that reads escapes twice sends to `evil.example`; nor do brackets hold a name, as `[paypal.com]`. An address is ASCII, as an `http` link's host is, below, since a character beyond ASCII may look like another. In a domain, a letter of another script may, as the Cyrillic `а` (U+0430) of `mailto:support@pаypal.com` looks like a Latin `a`, so that a mail client would show a domain that the message does not go to: an internationalized domain is written as IDNA writes it in ASCII, as in `mailto:keeper@xn--caf-dma.example`. In a local part, before the `@`, which a reader sees before the domain, a character beyond ASCII may look like a delimiter of an address, which may be punctuation, as U+FF20 FULLWIDTH COMMERCIAL AT (`＠`) looks like `@`, or a letter, as U+02BA MODIFIER LETTER DOUBLE PRIME (`ʺ`) looks like `"` and U+1438 CANADIAN SYLLABICS PA (`ᐸ`) like `<`, so that `mailto:ʺsupport＠paypal.comʺᐸx@evil.example` would read as a display name, `support@paypal.com`, and an address; or show as a blank as wide as a letter, which may be a symbol, as U+2800 BRAILLE PATTERN BLANK, or a letter, as U+13441 EGYPTIAN HIEROGLYPH FULL BLANK, a run of which after `support＠paypal.com` would push `@evil.example` out of what a mail client shows of the address. No property of Unicode's tells those from the letters, marks, and numbers of an internationalized address's local part (RFC 6532), so the address of a `mailto:` link has none, and `mailto:élodie@xn--caf-dma.example` is refused, and a client checks an address as the server does, whatever the version of its Unicode tables. A `subject` escapes no character that text may not hold, a control character (`Cc`) but a tab, as `%0A`, `%7F`, or `%C2%85`, a bidirectional control, as `%E2%80%AE`, which would reorder the subject that a mail client shows, or a line or paragraph separator, `%E2%80%A8` or `%E2%80%A9`, which a mail client could write into a header, as a line break that starts another, or a reader of lines take for a line break, as Python's `str.splitlines` takes NEL (`%C2%85`) and U+2028; it may escape a tab and other white space, and the format characters that are not bidirectional controls, which text may hold. A `body` may escape any byte: its line breaks are `%0D%0A`, as RFC 6068 writes them.
- `http://` or `https://`, followed by an authority, what is before the first `/`, `?`, or `#`, which is a host, then `:` and a port when it has one. The authority has no `@`, so a link has no userinfo, which would show a host that the link does not lead to, as `https://example.com@evil.example/` leads to `evil.example`. The host is not empty, and is ASCII. When the authority starts with `[`, the host is what the brackets hold, an IPv6 address as RFC 4291 (section 2.2) writes it, without a zone: eight groups of one to four hexadecimal digits, in either case, separated by `:`, of which one run of one or more groups of zeros may be written as `::`, and the last two of which may be written as an IPv4 address, below; and the `]` is followed by nothing or by `:` and the port. Otherwise the host is a name, which the last `:` of the authority, when it has one, separates from the port: ASCII letters and digits and the characters ``-._~!$&'()*+,;=``, in labels that `.` separates, of which none is empty but a last one after a `.` that ends the name, as in `example.com.`. When the name's last label, without that empty one, is ASCII digits, or `0x` or `0X` and hexadecimal digits, which a browser then reads as an IPv4 address, the name is one: four numbers from 0 to 255 in decimal, without leading zeros, separated by `.`, as `192.0.2.1`, so `https://999/`, `https://127.1/`, and `https://example.123/` are refused. The port is ASCII digits whose value is at most 65,535, as `08080` is 8080, or nothing. So `https://:80/` has no host, and a backslash, which a browser reads as a slash, cannot hide another host in the authority, as in `https://example.com\@evil.example/`, nor can a character beyond ASCII, which may look like another: a letter as a slash, as U+30CE KATAKANA LETTER NO (`ノ`), a digit as a dot, as U+0660 ARABIC-INDIC DIGIT ZERO (`٠`), or a symbol as either, as U+2215 DIVISION SLASH, all of which IDNA keeps in a host, so `https://bank.exampleノlogin.evil.example/`, which reads as a path of `bank.example`, leads to a host of `evil.example`. An internationalized host is written as IDNA writes it in ASCII, as `xn--caf-dma.example` for `café.example`, which is what a browser's URL parser gives as a URL's host (`new URL(href).hostname`), so the editor writes a link's host so before it sends the document. Whether a label that starts with `xn--` is one that IDNA writes is not checked, as whether a host exists is not: such a link leads nowhere, rather than elsewhere. Nor is what such a label stands for checked for characters that look like others, as `xn--pypal-4ve.com` stands for `pаypal.com`, with the Cyrillic `а`, in a host or in a `mailto:` link's domain: a browser or a mail client that shows such a name decoded does so by rules of its own, as a browser shows a label that mixes scripts as IDNA writes it, and a check by Unicode's tables of confusable characters, which change with each version of Unicode, would have a client and the server disagree on which links they take.

What follows the authority, and the value of a `mailto:` link's `subject` or `body`, may hold any character but those above, as `|`, `{`, and `@`. These are the rules, rather than what a URL parser takes, since parsers differ on what is not a URL. `javascript:`, `data:`, `file:`, and relative URLs are refused.

### Limits and what the server checks beyond the schema

Every document that the server accepts validates against the JSON Schema. The server also refuses what JSON Schema does not express, what the schema leaves out so that the API's tooling reads it, and what its patterns could name only as characters that would reorder how it shows (PRD NFR-SEC-07):

- A document of more than 1 MiB (1,048,576 bytes of UTF-8) of JSON, counted without the white space between its tokens and with each escape in a string, as `\"` or a `\u` escape, counted as the bytes of the UTF-8 of the character that it stands for, and an escaped surrogate pair as the one character that it stands for, so that whether a document is within the limit depends neither on how it is laid out, as PostgreSQL's `jsonb` lays it out, with a space after each `:` and `,`, nor on which characters its encoder escapes, as Go's `json.Marshal` escapes `<`, `>`, and `&`, and Python's `json.dumps` every character beyond ASCII; or whose canonical form, below, is longer than 1 MiB, which it can be when the JSON writes a number shorter, as `9e5` for 900000, so that every document that the server accepts can be written and read again.
- A document whose texts hold more than 100,000 characters together, counted as code points.
- A text with a bidirectional control, which the schema's pattern could name only as the character itself, as Go's regular expressions and ECMAScript's share no escape of a character beyond U+00FF, and which JSON writes as it is, so that it would reorder how the schema and the API's OpenAPI document show.
- Lists nested more than 5 deep: a list in no list is at depth 1.
- `attrs` on a `bulletList`.
- A list item that does not start with a paragraph.
- A mark twice, as two links, or the code mark with another.
- A link that the rules above refuse beyond the schema's pattern, which checks its scheme and refuses ASCII white space and control characters: one with white space beyond ASCII, a format character, or another character that a renderer shows nothing of, a `%` that starts no escape, an authority without a host or with a character that it may not hold, as an `@` or a character beyond ASCII, a name with an empty label or that a browser reads as an IPv4 address that is not one, brackets that hold no IPv6 address, a port that is not a number or is above 65,535, or a `mailto:` link with a `#` or a `;`, an `&` or an `=` in its address, a `?` or an `=` in a field's value, a field other than those above, escapes that are not UTF-8 outside a `body`, an escape that its address, a `to`, `cc`, `bcc`, or `subject` may not hold, an address that is not a local part, `@`, and a domain as above, as one with a display name, a comment, or quotes, or with a domain that holds what no domain that a message can be sent to holds, or brackets that hold no IP address, or an address with a character beyond ASCII.
- A string that escapes a lone surrogate, as `"a\ud800b"`, which is no character and which no UTF-8 holds. `JSON.parse` keeps it in the string, where Go would read U+FFFD, so the server refuses the document with `invalid_json`, and so does the client.

The vectors mark each document of these that the schema accepts with `schema_accepts`.

### The canonical form

The server stores a document in its canonical form, which it is the same however it was sent:

- No field holds its default: no empty `content` or `marks`, and no `attrs` of an ordered list that starts at 1.
- An inline node's marks are in alphabetical order: `bold`, `code`, `italic`, `link`, `strike`.
- A paragraph's neighbouring texts with the same marks are one text, as ProseMirror joins them.
- An ID is in its canonical spelling.
- Every object's keys are sorted, and HTML is not escaped.

### Errors

The server refuses a document that it reads with a reason and a JSON Pointer (RFC 6901) to the value that is wrong, within the document, though the API validates a request against the JSON Schema before, as the end of this section says. When a field is missing, the pointer is the object that misses it; when a document is too large, the pointer is the document's, `""`. A document with more than one thing wrong is refused at one of them, which implementations need not agree on: the server checks in an order of its own, and of several fields that an object may not have it names the first in the order of their code points, which is not the order of JavaScript's `sort`, of UTF-16 code units. So each invalid vector has one thing wrong.

The API validates a field of rich text against the JSON Schema before the server reads the document in it, as it validates the rest of a request's body. So a document that the schema refuses is refused as any invalid body is, with the validator's message rather than with a reason. The validator, huma, validates a node or a mark against each member of the `oneOf` of blocks, inline nodes, or marks, and keeps none of their problems, so it refuses a node or a mark that the schema does not take, or that holds a value that the schema does not take, at the outermost block that holds it, with `expected value to match exactly one schema but matched none`: a `javascript:` link in a list that is a document's second block is refused at `content[1]`. It refuses a problem outside the blocks at its place, as at `content` for a document without blocks. The schema has no `discriminator`, which would have huma validate a node or a mark against its `type`'s definition alone, and refuse it at the value that is wrong, since huma (v2.39.1) mishandles one: at each object without a `type`, or whose `type` is neither a string nor `null`, it adds a segment to the location of every problem that follows in the body, so that a body of many such objects costs it memory that grows with the square of their number. The server answers with a reason and a pointer for the rest: what the schema accepts, as the vectors marked `schema_accepts`, and a `null` in an optional field, which the validator lets through. The client's own validation, by this README and the vectors, gives every refusal its reason.

| Reason | Meaning |
| --- | --- |
| `invalid_json` | The input is not one JSON value in UTF-8, or one of its strings escapes a lone surrogate. |
| `wrong_type` | A value has another JSON type than the schema's, as a string for an array, `null`, or a number that is not an integer. |
| `unknown_node` | A node's `type` is not one of the schema's. |
| `unknown_mark` | A mark's `type` is not one of the schema's. |
| `unknown_field` | An object has a field that the schema does not give it. |
| `missing_field` | A field that the schema requires is missing. |
| `content` | A node is where its parent may not hold it, as a list in a paragraph or a list item that starts with a list, or a content that must hold a node is empty. |
| `empty_text` | A text's `text` is empty. |
| `control_character` | A text holds a control character but a tab, a bidirectional control, or a line or paragraph separator. |
| `duplicate_mark` | A node has a mark twice. |
| `excluded_mark` | The code mark is combined with another. |
| `link` | A link's URL is not an allowed one. |
| `reference` | An ID is not one, or of another type than it must be, or a value names an attribute of a variable, or none of a component. |
| `out_of_range` | An integer is outside its range. |
| `too_deep` | Lists nest more than 5 deep. |
| `too_large` | The document has more than 1 MiB of JSON, without the white space between its tokens and with its escapes counted as the characters that they stand for, or in its canonical form, or 100,000 characters of text. |

## Segments

The published format holds a document as its segments, which a runtime walks instead of the document's tree (PRD §6.1): a node's `text` and a connection's `label` are `{"segments": [...]}`, and a node's text also has a `preview`. The segments are the document's inline nodes in order, each with its marks, and segments that mark where its paragraphs, list items, and line breaks begin. A paragraph segment begins each paragraph but the document's first and the first of each list item, which an item segment begins instead. So a document of one paragraph has no segment that is not inline, and an empty document has no segment at all, and nor does a document's empty first paragraph.

| `kind` | Fields | Is |
| --- | --- | --- |
| `text` | `marks`, `value`, `href` | Text. |
| `mention` | `marks`, `ref`, `value`, `href` | A mention of component `ref`, whose name, when the snapshot was published, is `value`. |
| `value` | `marks`, `ref`, `attribute`, `decimals`, `name`, `href` | A value, of variable `ref`, or of the attribute `attribute` of component `ref`, shown with `decimals` when it has them. `name` names it as an expression does, as `met_elara` or `elara.trust`, for debugging, as an expression's AST names what it refers to. |
| `break` | — | A line break. |
| `paragraph` | `depth` | A paragraph begins. It belongs to the list item at `depth`, or to none when there is no `depth`. |
| `item` | `depth`, `list`, `number` | A list item begins: an item of a `bullet` or an `ordered` list, at `depth`, from 1, and an ordered list's item has its `number`. |

`marks` lists an inline segment's marks in alphabetical order, and is there, empty, when it has none. `href` is the URL of the link that an inline segment is part of. A `hardBreak`'s marks are in no segment.

```json
[
  { "kind": "text", "marks": [], "value": "Pack:" },
  { "depth": 1, "kind": "item", "list": "bullet" },
  { "kind": "text", "marks": ["bold"], "value": "Rope" },
  { "depth": 2, "kind": "item", "list": "ordered", "number": 3 },
  { "kind": "text", "marks": [], "value": "Oil" },
  { "kind": "paragraph" },
  { "kind": "text", "marks": [], "value": "Then go." }
]
```

## Plain text, preview, words, and hash

The text export (FR-TEXT-05) and the writing statistics (FR-TEXT-06) read a document's plain text, derived from its segments:

- **Plain text.** The texts and the mentions' names as they are, and each value as its `name` in braces, as `{met_elara}`. Each `paragraph` and `break` segment is a line feed, and so is each `item` segment but one that is the first segment. So a document that starts with a list starts with its first item, as does one whose empty first paragraph a list follows, since its segments are the same; but a document whose first segment is a `break`, or a `paragraph` after an empty first paragraph, starts with a line feed. An item segment then writes two spaces for each list that holds its list, and `• ` (U+2022 and a space), or its number and `. `. A `paragraph` or `break` segment within a list item then writes two spaces for each depth, which is as far as a bulleted item's text but not always as far as a numbered one's: `9. a`, a line break, and `b` are `9. a\n  b`. The segments above are `Pack:\n• Rope\n  3. Oil\nThen go.`.
- **Preview.** The plain text with each run of white space written as one space and none around it. When that is longer than 100 code points, it is cut after its first 100, and the preview is what comes before the cut, without the space at its end, and an ellipsis (`…`, U+2026). When the cut falls within a word, before a code point that is not a space, it goes back to the last space among the 100 if at least 50 code points come before that space, so that no word is cut. Otherwise, as in Chinese or Japanese, which separate no words with spaces, or within a word longer than half the preview, as a URL, it stays within the word, but goes back to the start of the character that it falls within, so that no character loses what continues it: back while the code point after it is a mark (Unicode's `M`, as U+0301 COMBINING ACUTE ACCENT, a vowel sign, or a variation selector), a `Grapheme_Extend` character, as a tag of a flag's emoji, a join control (`Join_Control`, U+200C and U+200D), or an emoji modifier (`Emoji_Modifier`, a skin tone, U+1F3FB to U+1F3FF), or the code point before it is U+200D ZERO WIDTH JOINER, as within the emoji of a family, or it falls between two regional indicators after an odd number of them in a row, as within a flag; and when that takes it back to the start, it stays at 100 code points, so that the preview is not empty. These are some of the rules of Unicode's grapheme clusters (UAX #29), rather than all of them, which `Intl.Segmenter` reads by tables of another version than the server's. The marks and the `Grapheme_Extend` characters are those that the server's tables have, as Unicode 15.0 has them, so a client whose tables are newer may cut a preview elsewhere in text with the marks that Unicode has assigned since, which no vector holds.
- **Words.** The words of the plain text without the bullets and numbers of its list items. A word is a run of characters that are not white space (Unicode's `White_Space`) with at least one letter or number among them (Unicode's `L` and `N`), so a dash between spaces is no word, and a run of Chinese or Japanese without spaces is one. The letters and numbers are those that the server's tables have, as Unicode 15.0 has them, the version of Go's package `unicode`. A JavaScript engine's tables are newer, and have as letters and numbers too the thousands that Unicode has assigned since, as the CJK ideographs of Extension I (U+2EBF0 to U+2EE5D) and the letters of scripts that it added, as Garay, so a client that reads `\p{L}` and `\p{N}` counts a word where the server counts none in a run whose only letters and numbers are among them, which no vector holds. Where two counts must agree, as the text export's and the writing statistics' (PRD FR-TEXT-05 AC3), one implementation counts both.
- **Hash.** `sha256:` and the lowercase hexadecimal SHA-256 of the plain text's UTF-8.

The limits above bound a document, not what is derived from it: a mention's segment and the plain text hold its component's name, and a value's segment its `name`, which the plain text writes in braces, none of which the document holds, and a line break within a list item writes its indentation. So a document within the limits may derive segments and a plain text of more than 100,000 characters, as many more as the names of its mentions and values are long: a document of 1 MiB holds more than 15,000 mentions.

## The vectors

| Key | Contents |
| --- | --- |
| `names` | The names that the derivations show: each component's in `components`, and each value's in `values`, a variable's by its `ref`, and an attribute's by its `ref` and `attribute`. |
| `valid` | Documents that the server accepts, with their canonical form in `canonical` when it is not the document itself, their `segments`, and their plain `text`, `preview`, `words`, and `hash`. A canonical form, a document that is its own, and the segments are written as the server writes them, with each object's keys sorted and HTML not escaped, so that an implementation compares the bytes that it writes with theirs, once the white space between their tokens is taken out. |
| `invalid` | Documents that the server refuses, with the `reason` and the `pointer` of the error, and `schema_accepts` when the JSON Schema accepts them. Each has one thing wrong with it, so that every implementation reports the same one. |
| `words` | Texts and their number of words. |
| `previews` | Plain texts and their previews. |
| `lengths` | JSON texts of one document, written in several ways, as `jsonb` and Python's `json.dumps` and Go's `json.Marshal` write it, and the `length` that the limit of 1 MiB counts for each, which is the same. |

A `note` says what a vector is for. The hashes and the lengths were computed independently of the Go implementation, with Python's `hashlib` and the rules above. The limits on a document's size are tried by the Go tests rather than by vectors, which would need a megabyte of JSON each; `lengths` holds how a document's JSON is counted against them.
