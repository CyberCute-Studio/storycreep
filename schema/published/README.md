# The published game format

The published game format is what a game runs its narrative from: a snapshot's files, which the Godot addon pulls into `res://storycreep/` (PRD §6). This directory holds the JSON Schema of each of its files, by the format's version, `schemaVersion`, of which only 1 exists. The save state that a runtime writes is a format of its own, versioned apart, in [`../save-state/`](../save-state/).

| Document | Describes |
| --- | --- |
| [`v1/storycreep.schema.json`](v1/storycreep.schema.json) | `storycreep.json`, the manifest. |
| [`v1/settings.schema.json`](v1/settings.schema.json) | `project/settings.json`. |
| [`v1/variables.schema.json`](v1/variables.schema.json) | `project/variables.json`. |
| [`v1/component_types.schema.json`](v1/component_types.schema.json) | `project/component_types.json`. |
| [`v1/components.schema.json`](v1/components.schema.json) | `project/components.json`. |
| [`v1/board.schema.json`](v1/board.schema.json) | `boards/<slug>.json`, one board's file. |
| [`v1/ast.schema.json`](v1/ast.schema.json) | An expression's AST, which a board's file holds beside the expression's source (PRD §5.8.8). |

Each document is generated from the Go types of [`server/internal/published`](../../server/internal/published) by [`server/internal/schemagen`](../../server/internal/schemagen), and so are the web app's TypeScript types, `web/shared/src/published/v1.gen.ts`, from the documents (PRD FR-DATA-04). `go test ./...` fails when a document or the TypeScript is not what the Go types generate; `go test ./internal/published -run 'TestSchemaFiles|TestTypeScript' -update`, in `server/`, rewrites them. A document's `$id` is the URL of its file on the main branch, which names the format's version, as `…/schema/published/v1/board.schema.json`, so that a consumer pins a version by it (AC3). Each document holds every definition that it refers to, so that it validates its file alone, and its examples, which describe one project, Harbour, the PRD's, whose expressions are what the server compiles their sources to and whose texts what it derives of their rich text.

## What every file holds

These rules are of every file, and of the save state too (PRD §6.2, §6.4):

- **No null.** A field that is not set is left out, never `null`, and every schema refuses `null` wherever it is, a key that the schema does not define included. So does `published.Decode`, the Go types' reading of a file.
- **Keys that a consumer does not know.** An object may hold a key that its schema does not define, of any value but `null`, at any depth (`AnyValue`), which a consumer ignores, so that a later server may add an optional field without a new `schemaVersion`. A consumer reads a key as it is written, so that one that differs from a key that the schema defines only by its case, as `KIND` from `kind`, is such a key. A closed variant of the schemas, which takes no such key, checks the examples in the tests.
- **Values that a consumer does not know.** A field of an enum, as a `type`, a `kind`, an `op`, a snapshot's `channel`, or a variable's `scope`, holds one of the values that its schema lists, and a consumer fails loudly on any other (§6.4), as `published.Decode` does.
- **Variants.** A node is an element, a branch, or a jumper, by its `type`, and a manifest's snapshot a release or a draft, by its `channel`. Each variant takes no key that another variant of its union defines and it does not, which TypeScript types as `never`, so that a jumper has no `text` and a draft no `version` (§7.8): a runtime reads a node's or a snapshot's fields by their names. So a field that one variant has is added to another only with a new `schemaVersion`. A variable is a variant of its `scope` and its `type`, of which a board's alone has `boardId` and `resetOnEnter`; an attribute definition of its `type`, of which an enum's alone has `options`; and a branch's output of its `kind`, of which `if` and `elseif` have a `condition` and `else` none.
- **Numbers typed by their declaration.** A number is read as its declaration types it, never by how its JSON writes it (§5.8.9): a variable's `default` by its `type`, an attribute definition's `default` and a component's value of it by the definition's `type`, and a literal's `value` by the literal's `type`, so that an `int` written `2.0` is 2. A schema types what it can: a value whose declaration is in another file, as a component's value of an attribute, is any boolean, number, or string (`Value`). Every integer of the format's own, as a connection's `order`, a manifest's `counts`, or a list item's `number`, is an `integer`, which JSON Schema takes written as `2.0` too, and which a consumer reads so, of at most 2^53 − 1, the greatest up to which a double holds every integer. A `float` is within ±1.7976931348623157e+308, the greatest double as its shortest form writes it, which JSON Schema compares with the number's value as it is written, so that the schemas, `published.Decode`, and `expr.Decode` refuse `1.7976931348623158e308` too, which a double reads as the greatest double, where they know that it is a `float`; a validator that reads every number as a double, as one in JavaScript or GDScript does, cannot tell it from the greatest double, and takes it, which no file that the server writes holds. A number's exponent, if it has one, is within ±999, as every number that the server writes is: JSON Schema cannot say how a number is written, so the schemas take `0e1000` as 0, but `published.Decode` and `expr.Decode` refuse it, wherever it is.
- **Optional fields.** A field that its schema does not require is left out when it is not set, as a node without a title has no `title`, an element with empty text no `text`, a connection without a label no `label`, and an element without tags no `tags`. An array that is a structure's, as a branch's `outputs`, a call's `args`, or a script's `statements`, is there when it is empty, as `[]`.
- **Order.** An array is in the order that its author gave it where that order means something: a type's attribute definitions, a branch's outputs, a node's tags, a rich text's segments, a script's statements, and a call's arguments. Every other array is sorted by its items' `id`, and a settings file's `signals` by their code points. A connection's `order` is its place among the connections that leave its port, from 0, which is the order of its choice.
- **IDs.** Every ID is in its canonical spelling, its lowercase prefix and its uppercase body (§5.2), so that a consumer compares IDs as strings.

## The files

- **`storycreep.json`.** The manifest: the snapshot's `project`, its `schemaVersion` and `astVersion` (FR-EXPR-04), the `generator` that wrote it, its `counts`, its `entry`, the `boards` index, by which a runtime finds a board's file without reading another (§6.5), the hash of each other file in `files`, by its path, and the `snapshot`: a release's `id`, `version`, `note`, `publishedAt`, and `contentHash`, or a draft's `pulledAt` and `contentHash`, without an ID or a version (§7.8). A moment is in UTC, to the second. The manifest is not in its own `files`.
- **`project/settings.json`.** The project's `entry`, as the manifest's, and the `signals` that its scripts emit with `signal()`, which a runtime's `list_signals()` returns (§8.4.1). No project-level flag exists yet; one would be an optional field, and so would the host functions of FR-EXPR-05 (v1).
- **`project/variables.json`.** Every variable, global and of each board: its `id`, `key`, `scope`, `type`, `default`, and `description`, and a board's `boardId` and `resetOnEnter`, which is left out when it is false.
- **`project/component_types.json`.** Each component type that a component is of, with its attribute definitions: each one's `id`, `key`, `name`, `type`, `default`, `runtime` flag, and an enum's `options`. A definition that is not `runtime` is a game's static data, as a character's title, which expressions do not read.
- **`project/components.json`.** Each component: its `id`, `key`, `name`, `componentTypeId`, `image`, and a value of each attribute definition of its type, runtime or not, by the definition's ID, in `attributes`. Its rich-text description is for its authors, and is in the authoring export alone.
- **`boards/<slug>.json`.** The `board`, its `nodes`, and its `connections`. An element has its `kind`, `title`, `text`, `speaker`, `cover`, `tags`, `position`, `isEnding`, and its `onEnter` and `onExit` scripts; a branch its `title`, `position`, `outputs`, and scripts; and a jumper its `title`, `position`, and `target`. A connection leaves its node `from` by its `fromPort`, an element's `out` or a branch's output's ID, for its node `to`, with its `order`, its `label`, its `condition`, and its `onTraverse` script. An element's `text` is its rich text's `segments` and its `preview`, and a connection's `label` its segments, as [`../rich-text/README.md`](../rich-text/README.md) describes them. An image, a cover's or a component's, is an asset's ID, whose file is `assets/<the ID's body>.<its extension>` when the snapshot includes assets.
- **Expressions.** A condition and a script are their `source`, as their author wrote it, and their `ast`, of which a condition's is an expression and a script's a `script` node (`v1/ast.schema.json`), its names resolved to the IDs of what they name. A runtime evaluates the AST, and parses no source.

## What a consumer checks beyond the schemas

JSON Schema does not reach across files, nor say what each item of an array must be beside the others. `Validate` in the addon, a runtime's loader, and the server, which validates every file that it builds (plan item 78) and imports (item 84), check these too:

- Every board of the index has its `file` in `files`, every path of `files` is one of the forms of the pull's path rules (PRD §7.5), whose slug is not a name that Windows reserves for a device, and every file's hash is its bytes'.
- Every reference resolves: the entry's node is a node of its board, as is a board's `entryNodeId`; a connection's nodes are nodes of its board, its `fromPort` the `out` of an element or an output of its branch; a jumper's target is a node of its board that is no jumper; a speaker, a mention, and a value refer to a component or a variable that the snapshot has, and an attribute to a definition of the component's type; a component's type is one of `component_types.json`'s; a variable's board is one of the index's; and an AST's names resolve, by their refs, and type-check against the snapshot's declarations (FR-DATA-01): its JSON holds neither the scope that a variable's source qualified it with nor an attribute's `cmp.`, so its names are not resolved anew by their keys, which `expr.Check` does of a parsed source's.
- A component has a value of each definition of its type and of no other, of the definition's type, an enum's one of its options; an enum definition's `default` is one of its options; a definition that is a `text` is never `runtime`; and an enum's options are each there once.
- The files agree: each board of the manifest's index has the `id`, `name`, `slug`, and `entryNodeId`, or none, that its file's `board` has, and its `file` is `boards/` and its slug and `.json`; the settings' `entry` is the manifest's, or neither has one; and the manifest's `counts` are how many boards, components, connections, nodes, and variables the files hold.
- An inline segment's `marks` are each there once, in alphabetical order, and `link` is among them exactly when the segment has an `href`.
- No two entities have one ID; no two variables of a scope, no two components, no two component types, and no two definitions of a type have one key; no two tags of a node are the same but for their case; no signal is there twice; a branch's first output is its `if`, its `else`, if it has one, its last, and its outputs' and a port's connections' `order`s are 0, 1, 2, and so on.

`published.Decode` reads a file into the Go types. It refuses exactly these, and nothing else: a file that is not UTF-8, `null`, a lone surrogate escaped in a string, a number written with an exponent beyond ±999, a key that the schema requires that is missing, a value of an enum that the format does not have, another `schemaVersion`, a key of a variant that is there, whatever its value, where its variant does not have it, as an `else` output's `condition`, a global variable's `boardId`, a draft's `version`, or a jumper's `text`, or that is missing or empty where its variant requires it, as an `if` output's `condition` or an enum's `options`, a key that is there without the key that it is there with, or that is not empty where that key is empty, which the types leave out, as a save state's `snapshotId` without its `snapshotVersion`, or with an empty one, a value that is not of its declaration's type, or that is neither a boolean, a number, nor a string where its declaration is in another file, an empty text or label, which a file leaves out, and an AST that `expr.Decode` refuses, as one whose names are not resolved; and ignoring what it does not know, a key that differs from one that it knows only by its case included, but for a map's keys, as `files`' paths, which it reads as they are written; and of a key that an object has twice, it reads the last. A file that it reads may still be one that the schemas refuse: it does not check their patterns and bounds, which a validator of the schemas checks (plan items 78 and 84), but for an integer's, of at most 2^53 − 1, and a `float`'s, within ±1.7976931348623157e+308 as it is written. The Go types refuse to write a file that it would refuse.

## Adding a document

The diff structure (plan item 80) and the authoring export (item 83) add their documents through the same generator: Go types whose fields' tags constrain them, as `schemagen.Generator` lists, and a `schemagen.Document` of each, generated with the published format's definitions by one generator, so that a definition that two documents hold is the same in both.
